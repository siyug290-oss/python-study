## 今天学了

- **数据结构变更**：`list[str]` → `list[dict]`。**一个字符串里放不下"内容 + 完成没完成"两样东西**
- **嵌套结构怎么一层层访问**：列表用**位置**，字典用**键**。`self.items[0]["done"]`
  —— 前面那个方括号是在列表上按位置取，取出来的是字典；后面那个才是在字典上按键取
- **三元表达式**：`值A if 条件 else 值B`。它本质上是**表达式**（能塞进 `=` 右边、能塞进 `print()`），
  而 `if/else` 是**语句**（只能独立站着）——**这才是它存在的理由**，不只是"少写几行"
- **真值性**：Python 里任何东西都能当条件。**空的、零的、没有的都是假**
  （`""` / `[]` / `{}` / `0` / `None` 假，其余真）。所以 `if t["done"]:` 就够了，不用写 `== True`
- **`is` 和 `==`**：`==` 问"值相等吗"，`is` 问"**是不是同一个对象**"。
  `1 == True` 是 `True`，但 `1 is True` 是 `False`
- **`enumerate(x, n)`**：一边遍历，一边给出"这是第几个"；`n` 是"编号从几开始"（默认 0）
- **HTTP 方法**：`GET` 读 ｜ `POST` 提交一个动作 ｜ `PUT` 整体替换 ｜ `PATCH` 局部改 ｜ `DELETE` 删
- **路径风格和方法是配套的**：路径以**名词**结尾 → 资源型（配 `PATCH`）；
  以**动词**结尾（`/todos/3/done`）→ 动作型（配 `POST`）
- **测试的两种测法**：验"返回值"和验"结果"。后者值钱，因为它能抓住前面验不出的错

## 卡在哪

### 1. 括号有三种身份，我搞混了

```python
self.items[index-1][{"done"}] = True     # ❌
self.items[index-1]["done"] = True       # ✅
```

**现象**：`TypeError: cannot use 'set' as a dict key (unhashable type: 'set')`

**原因**：`{"done"}` 是**集合（set）**，不是字典的键。三种括号完全不是一个东西：

| 写法 | 是什么 |
|---|---|
| `{"done"}` | 集合 —— 里面装着一个元素 |
| `{"done": True}` | 字典 —— 一个键值对（**关键在冒号**） |
| `["done"]` | 列表 —— 里面装着一个元素 |

方括号里放的是**键**，而**键必须是不可变的**（字符串、数字、元组）。
集合是可变的，所以不能当键。

**这是"可变 / 不可变"第一次真的咬到我。**

### 2. `for i in enumerate(...)` 只写了一个变量

```python
for i in enumerate(items, 1):            # ❌
for i, t in enumerate(items, 1):         # ✅
```

**现象**：`NameError: name 't' is not defined`——第 6 行在用 `t`，但 `t` 从没被创建

**原因**：`enumerate` 每轮返回的是一个**配对** `(序号, 元素)`。
**变量个数必须和配对里的元素个数对上。** 只写一个，那个变量就装下了**整个配对**；
写两个，配对才被拆开分给它们。

```python
for x in enumerate(["a", "b"], 1):
    print(x)        # (1, 'a')    ← 一个变量：整个配对

for a, b in enumerate(["a", "b"], 1):
    print(a, b)     # 1 a         ← 两个变量：拆开了
```

这个"把配对拆给几个变量"的动作，叫**解包**。

### 3. `t.["done"]` 多了一个点，但报错指向别处

**现象**：

```
    mark = "[x]" if t.["done"] else "[ ]"
           ^^^^^^^^^^
SyntaxError: expected 'else' after 'if' expression
```

报错说"`if` 后面少了 `else`"——**听起来像三元表达式写错了。**

**原因**：那个三元表达式**完全没问题**。是 `t.[` 把解析器带偏了：
`.` 后面**必须跟一个名字**（属性名或方法名），而 `[` 不是名字。

**真正的教训：报错信息会骗人。** 当它说的位置和你写的位置对不上时，
**往前多看一两个词**。

两类成员访问不能混：

```python
self.items.append(...)    # ✅ 点 + 名字
t["done"]                 # ✅ 方括号 + 键
t.["done"]                # ❌ 混在一起
```

## 今天最重要的三个收获

### 一、改数据结构 = 动地基

改的不是某个函数，是 **`items` 里装什么**。装什么一变，所有碰 `items` 的代码都得跟着变：
`add()` / `show()` / `done()` / 测试 / 接口 / 连 `todo.json` 的文件格式都变了。

**而且旧数据直接失效**——`todo.json` 里还是字符串，读出来当字典用会崩，只能删掉重来。

这是**"数据结构迁移"的最小版本**。以后换数据库会遇到同一件事，只是规模大得多。

### 二、测试在"改地基"的时候才显出价值

9 条老测试**一条都没改**，改完数据结构跑 `pytest`，**0.03 秒确认"老功能一个没坏"**。

没有测试的话，我得手动点一遍 `cli.py`：添加、删除、显示、退出重进……还未必想得全。

**测试不是让你现在少出错，是让你以后敢改。**

**还有一条**：测试要**能失败**才有意义。
`undone` 的测试必须**先 `done(1)` 再 `undone(1)`**——不然 `done` 本来就是 `False`，
断言怎么都会过，**等于没测**。

### 三、今天三个坑全是"符号"层面的错

花括号当键、少写一个变量、多一个点——**没有一个是逻辑错，全是符号写错**。
而且其中两个的报错信息**都指向了别处**。

**结论：读报错时先怀疑符号，别急着怀疑逻辑。**
